## Итерация 2 — потоки (ThreadPoolExecutor)

Файл: `integrate_threads.py` (`integrate_async`), замер в `bench_iter23.py`.

n_iter = 10⁵, cos(x) на [0, π/2]:

| n_jobs | время / вызов |
|---|---|
| 1 | 9.070 мс |
| 2 | 6.316 мс |
| 4 | 5.980 мс |
| 6 | 6.025 мс |
| 8 | 6.210 мс |

**Вывод**: небольшой выигрыш при переходе 1→2 потока (перекрытие
накладных расходов планировщика), но дальнейшего ускорения при росте
числа потоков НЕТ, время выходит на плато ~6 мс. Причина — GIL:
байткод-инструкции разных потоков CPython выполняются по очереди
(round-robin), реального параллелизма на CPU-bound коде нет.

Файл: `integrate_processes.py` (`integrate_process`), замер в `bench_iter23.py`.

| n_jobs | время / вызов |
|---|---|
| 1 | 97.6 мс |
| 2 | 90.8 мс |
| 4 | 107.9 мс |
| 6 | 136.3 мс |
| 8 | 155.7 мс |

**Вывод**: время не только не падает, но растёт с числом процессов —

больше) и/или переиспользовании одного и того же пула процессов
(`ProcessPoolExecutor` создан один раз, а не при каждом вызове).

## Итерация 4 — профилирование и Cython

Профиль (`profile_integrate.py`, cProfile, n_iter=10⁶):

```
1000002 function calls in 0.185 seconds
   ncalls  tottime  percall  cumtime  filename:lineno(function)
        1    0.136    0.136    0.185  integrate.py:7(integrate)
  1000000    0.048    0.000    0.048  {built-in method math.cos}
```

~74 % времени — сам Python-цикл (создание кадров, интерпретация
байткода арифметики), ~26 % — вызовы `math.cos`.

Cython-версия: `integrate_cython.pyx` (`cdef double acc/step`,
`cdef int i`, директивы `boundscheck(False)`, `wraparound(False)`),
сборка — `setup_cython.py` (`cythonize(..., annotate=True)` → генерирует
`integrate_cython.html` с построчной цветовой картой обращений к
C-API). Компилятор — GCC 16.2.0 (MinGW-w64 UCRT), т.к. Cython на Windows
не поставляет свой компилятор в отличие от Colab/Linux.

Сравнение (`bench_iter4.py`, f = x², n_iter=10⁶, 50 повторов):

```
Чистый Python : 79.953 мс/вызов
Cython        : 79.050 мс/вызов
Ускорение     : 1.01x
```

**Почему Cython почти не ускоряет** (это прямой ответ на вопрос из
ноутбука «почему в колабе cython-вариант вычисляется не быстрее»):
узкое место — не арифметика цикла (`acc`, `step`, `i` уже типизированы
в C), а **вызов `f(...)`**, где `f` — произвольный Python-объект
(функция/лямбда). Каждая итерация всё равно делает полноценный вызов
через Python C-API (`PyObject_Call`), с распаковкой и упаковкой
Python-объектов на вход/выход — это доминирующая часть времени, и
Cython её ускорить не может, т.к. по HTML-аннотации (`integrate_cython.html`)
именно строка с вызовом `f(...)` остаётся "жёлтой" (много обращений к
C-API), в отличие от типизированных `acc`, `step`, `i`, которые стали
"белыми" (чистый C).

**Как исправить**: типизировать саму интегрируемую функцию как C-функцию
(`cdef double f(double x) noexcept nogil`) вместо произвольного Python
callable — тогда вызов `f(x)` тоже станет прямым C-вызовом без выхода в
Python C-API. Именно это сделано в итерации 5 (`integrate_cos_nogil`,
интегрирует `libc.math.cos`) — там ускорение уже реально ощутимо (см. ниже).

## Итерация 5 — nogil

Файлы: `integrate_nogil.pyx` (функции `integrate_cython` — обычная,
и `integrate_cos_nogil` — с `with nogil:` вокруг цикла, вызывающая
`libc.math.cos`), сборка — `setup_cython_nogil.py`, собрана и для
обычного CPython 3.13.15, и для free-threaded сборки 3.13.15t
(`Py_GIL_DISABLED=1` в логе компиляции подтверждает нужный ABI).

### Ускорение потоков на nogil-функции (обычный GIL, `bench_iter5_nogil.py`)

CPython 3.13.15 (GIL включён), n_iter=10⁷:

| n_jobs | время | ускорение |
|---|---|---|
| 1 | 37.580 мс | 1.00x |
| 2 | 22.080 мс | 1.70x |
| 4 | 12.352 мс | 3.04x |
| 6 | 8.434 мс  | 4.46x |
| 8 | 8.091 мс  | 4.64x |

Даже с ВКЛЮЧЁННЫМ GIL потоки ускоряются, т.к. `with nogil:` в самой
Cython-функции явно отпускает GIL на время C-цикла — другие потоки
Python в это время могут выполняться.

### То же на free-threaded интерпретаторе (`PYTHON_GIL=0`)

| n_jobs | время | ускорение |
|---|---|---|
| 1 | 38.574 мс | 1.00x |
| 2 | 22.213 мс | 1.74x |
| 4 | 11.648 мс | 3.31x |
| 6 | 8.221 мс  | 4.69x |
| 8 | 7.165 мс  | 5.38x |

Ускорение чуть выше, чем на обычной сборке — на free-threaded
интерпретаторе полностью отсутствуют GIL-переключения даже между
Python-фрагментами кода (submit/as_completed), что даёт дополнительный
выигрыш при n_jobs=6–8.

### Потоки (nogil) против процессов на одинаковой Cython-функции

(`bench_iter5_threads_vs_processes.py`, free-threaded интерпретатор):

| n_jobs | потоки (nogil) | процессы |
|---|---|---|
| 2 | 22.652 мс | 105.336 мс |
| 4 | 12.233 мс | 99.254 мс |
| 6 | 8.929 мс  | 106.012 мс |
| 8 | 7.890 мс  | 118.281 мс |

**Вывод**: потоки с явно освобождённым GIL в Cython-коде дают
многопоточный параллелизм БЕЗ накладных расходов на межпроцессное
взаимодействие — при этой нагрузке они в 10–15 раз быстрее процессов.
Процессы имеют смысл только для намного более тяжёлых заданий на
воркер, когда фиксированные накладные расходы IPC становятся
пренебрежимо малой долей общего времени.

### * Примитивы синхронизации (семафор, мьютекс)

Файл: `sync_primitives_demo.py`.

В исходной архитектуре `integrate_async`/`integrate_process` каждый
воркер возвращает свой результат через `Future`, а суммирование
происходит в главном потоке после `as_completed()` — общих
изменяемых данных между потоками/процессами НЕТ, поэтому мьютекс или
семафор не нужны: гонки данных нет по конструкции задачи.

Синхронизация становится нужна, только если воркеры сами пишут в
общую структуру (продемонстрировано на `integrate_shared_no_lock` /
`integrate_shared_with_lock` — оба варианта дали идентичный корректный
результат `1.9999999999897224` на GIL-сборке, т.к. GIL и так
сериализует байткод и не даёт настоящей гонки на уровне `+=`). На
free-threaded сборке (без GIL) при реальном параллелизме такая гонка
уже возможна, и `threading.Lock` вокруг обновления общего аккумулятора
обязателен для корректности — иначе часть частичных сумм может быть
потеряна при одновременной записи.

### * Python 3.14

Запуск `bench_iter23.py` на штатном (не free-threaded) CPython 3.14.0:

```
=== Потоки (ThreadPoolExecutor) ===
n_jobs=1:    5.211 мс/вызов
n_jobs=2:    4.826 мс/вызов
n_jobs=4:    5.133 мс/вызов
n_jobs=6:    5.051 мс/вызов
n_jobs=8:    5.412 мс/вызов
=== Процессы (ProcessPoolExecutor) ===
n_jobs=1:   88.662 мс/вызов
...
n_jobs=8:  138.880 мс/вызов
```

**Вывод**: картина идентична итерации 2 (Python 3.11/3.13) — потоки на
чистом Python-коде в Python 3.14 по-прежнему не масштабируются. В
Python 3.14 GIL остаётся включённым по умолчанию (PEP 703 сделал
free-threaded сборку официальной, но опциональной — нужна отдельная
сборка `python3.14t` / флаг `--disable-gil` при компиляции, обычный
`python3.14.exe` собран с GIL). Поэтому для CPU-bound кода на чистом
Python отпускать GIL по-прежнему нужно вручную (Cython/C-расширения) —
сам факт перехода на 3.14 ничего не меняет без использования
free-threaded сборки.

## Итоговые выводы

1. Потоки на чистом Python не ускоряют CPU-bound код (GIL) — ни в
   3.11, ни в 3.13, ни в 3.14 (обычная сборка).
2. Процессы дают реальный параллелизм, но накладные расходы IPC делают
   их невыгодными для лёгких задач/малого n_iter.
3. Cython ускоряет только то, что реально переведено в C — типизация
   `acc/step/i` без изменения способа вызова `f()` почти не помогает,
   пока сам вызов идёт через Python C-API.
4. Явное освобождение GIL в Cython (`with nogil`) работает совместно с
   `ThreadPoolExecutor`, давая честный многопоточный параллелизм даже
   на обычной (не free-threaded) сборке CPython.
5. Free-threaded интерпретатор (3.13t, `PYTHON_GIL=0`) даёт
   дополнительный (не принципиальный, но измеримый) выигрыш поверх
   nogil-Cython при большом числе потоков.
6. Примитивы синхронизации нужны только при разделяемом изменяемом
   состоянии между воркерами — в данной задаче (сумма независимых
   Future) они избыточны.
